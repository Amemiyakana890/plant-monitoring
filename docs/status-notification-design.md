# 状態判定・通知設計(ドラフト)

> `system-design.md 5-7`(土壌水分のみの固定閾値ロジック)を拡張する提案。
> 数値はすべて「モンステラ・室内観葉植物」を想定した**暫定値**。
> 実測データが溜まった時点で調整すること(この文書内のTODOを参照)。

## 1. 全体方針(前提の再掲)

- 状態は **適正 / 注意 / 要ケア** の3段階
- 現在値だけで判定せず、植物種・季節・継続時間・過去データを考慮する
- 温度・土壌水分:基準外の**継続時間**で深刻度を上げる(影響が大きいため)
- 湿度・照度:**一定期間の平均・傾向**で判定する(一時的な変化で通知しない)
- 照度は夜間の低下が正常なため、**時間帯を考慮**する

## 2. 3段階の意味(共通定義)

| レベル | 意味 | ユーザーへの見せ方 |
|---|---|---|
| 適正 | 対応不要 | ホーム画面で緑表示。通知なし |
| 注意 | 近いうちに対応した方がよい状態 | ホーム画面で橙表示。通知は**状態が悪化した瞬間のみ**生成 |
| 要ケア | 速やかな対応が必要 | ホーム画面で赤表示。通知を生成。解消されず長引く場合はリマインドを1回追加 |

## 3. 項目別ロジック

### 3-1. 温度

| 段階 | 条件(暫定) |
|---|---|
| 適正 | 18〜30℃ |
| 注意 | 15〜18℃ または 30〜35℃ の範囲に**30分以上**継続 |
| 要ケア | 10℃未満 または 35℃以上(**即時**、継続時間を問わず) / もしくは「注意」の状態が**2時間以上**継続 |

- 10℃未満・35℃以上は霜害・熱ストレスのリスクが高いため、継続時間を待たずに即座に要ケアとする。
- TODO: 適温範囲(18〜30℃)は`plant_info_page.dart`のケアポイント文言からの暫定値。植物種マスタができたら種ごとに分離する。

### 3-2. 湿度(日次レポート型)

温度・土壌水分に比べて重要度が低いため、常時監視ではなく**1日1回・24時間平均で評価**するシンプルな方式にする。

| 段階 | 条件 |
|---|---|
| 適正 | 24時間平均が 60〜80% |
| 注意 | 24時間平均が 40〜60% または 80〜90% |
| 要ケア | 24時間平均が 40%未満 |

- 24時間の平均を使うこと自体が「一時的な変化を無視する」役割を兼ねるため、以前の版にあった「別途30分移動平均+2時間継続」のような複雑な継続時間トラッキングは不要になった(平均を取る時間の長さそのものが継続性のフィルタになっている)。
- 評価・通知は1日1回、15:00に実施する(詳細は6-5章)。

### 3-3. 土壌水分(季節依存)

| 季節 | 適正 | 注意 | 要ケア |
|---|---|---|---|
| 夏(6〜9月) | 40%以上 | 20〜40% | 20%未満 |
| 冬(12〜2月) | 30%以上(休眠期のため水やり頻度を落とす想定) | 15〜30% | 15%未満 |
| 春・秋(上記以外) | 35%以上 | 18〜35% | 18%未満 |

- 継続時間:「注意」は**6時間以上**継続した場合のみ通知対象とする(センサーのノイズや一時的な乾き方向の変動を無視するため)。「要ケア」は基本的に即時通知するが、**前回の水やりから2時間以内**であれば「センサーの応答遅れ・排水直後」の可能性があるため、通知は1段階抑えて「注意」扱いにする。
- 「前回の水やり」はセンサーからは分からないため、後述(4章)の通り**手動記録機能**が必要。
- TODO: 冬季30%・春秋35%は暫定値。実際の鉢の乾き方を見ながら調整する。

### 3-4. 照度(日次レポート型)

湿度と同様、重要度が低いため1日1回の評価にする。ただし夜間の暗さは正常な現象なので、
評価対象は**24時間全体ではなく「昼間(6:00〜18:00)の平均」**とする。
(24時間そのまま平均すると夜間の低照度に引っ張られて常に「不足気味」判定になってしまうため、照度のみ昼間平均とする。**この前提で確定**)

| 段階 | 条件 |
|---|---|
| 適正 | 昼間(6:00〜18:00)平均が 1,000〜10,000 lux |
| 注意 | 昼間平均が 500〜1,000 lux(やや不足) |
| 要ケア | 昼間平均が 500 lux未満(明確に不足) |

- 評価・通知は1日1回、15:00に実施する(詳細は6-5章)。
- 評価対象期間は**直近24時間**(現在から24時間前まで)とし、その中から昼間(6:00〜18:00)に該当する時間帯のデータだけを抽出して平均する。15:00に評価する場合、直近24時間には「前日15:00〜18:00」(3時間)+「当日6:00〜15:00」(9時間)が含まれ、合計でちょうど**丸1日分(12時間)の昼間データ**が確保できる(15:00という評価時刻はこの点でも都合が良い)。
- TODO: 「直射日光が強すぎる」ケース(20,000lux超など)は今回の簡易版では評価対象から外した。必要になれば別途追加を検討する。

### 3-5. 植物全体のステータス(plants.status)

4項目のうち**最も深刻なレベルを採用**(worst-of方式)。
例:温度=適正、湿度=適正、土壌水分=要ケア、照度=注意 → 全体は「要ケア」。

ホーム画面のメッセージ(例:「土壌水分が少なくなっています」)は、要ケア・注意と判定された項目のうち最も深刻なものを元に生成する。

温度・土壌水分はリアルタイム評価、湿度・照度は1日1回(15:00)の評価と更新頻度が異なるため、worst-of判定を行う瞬間には「湿度・照度は直近の確定済み日次評価(3-6章参照)」を使う。

### 3-6. ホーム画面での表示(湿度・照度)

湿度・照度は評価頻度が1日1回になったため、ホーム画面の見せ方を温度・土壌水分と分けて考える。

- **数値(実測値)は従来どおりリアルタイム表示**する(例:「222 lux」「75.9%」)。今の様子を見て楽しむ・安心する用途としてそのまま残す。
- **バッジ(適正/注意/要ケア)は「直近で確定した日次評価」を表示**する。
  - 当日15:00より前:前日の評価を表示
  - 当日15:00以降:その日15:00に確定した評価に切り替え
- 数値とバッジの評価タイミングがズレるため、混乱を避けるためバッジの近くに評価時刻を小さく添える(例:「(15:00時点の評価)」)。
- 初回セットアップ直後などまだ1回も日次評価が行われていない場合は、バッジを「評価準備中」のようなニュートラル表示にする(0件データでの誤判定を避ける)。
- この方式にすることで、「数値は良さそうなのにバッジは注意」のような瞬間的な矛盾を避けつつ、通知が届くタイミング(15:00)とバッジが切り替わるタイミングを一致させられる(「静かに見守る」体験と相性が良い)。

## 4. データモデルへの影響(提案)

現行スキーマ(`system-design.md 6章`)への追加案:

### 4-1. 種ごとの閾値マスタ(将来の複数種対応も見据えて)

```
species_thresholds
- id
- species (例: "モンステラ")
- temp_min / temp_max
- humidity_min / humidity_max
- illuminance_min / illuminance_max
- soil_threshold_summer / soil_threshold_winter / soil_threshold_default
```

v1は1種類(モンステラ)のみなので、テーブル化せず定数管理でも構わないが、
将来の複数植物対応(企画書11章)を見据えるとテーブル化しておくと移行が楽になる。

### 4-2. 水やり記録(土壌水分の「前回の水やり」判定に必須)

センサーだけでは「水やりした瞬間」は分からないため、記録機能自体を追加する必要がある。

```
watering_logs
- id
- plant_id (FK)
- watered_at
```

- 植物情報画面かホーム画面に「水やりしました」ボタンを追加し、タップでこのテーブルに記録する。
- 履歴画面のグラフ上に水やりタイミングをマーカー表示すると、土壌水分の推移と合わせて見やすくなる(将来拡張)。

### 4-3. 継続時間の追跡

湿度・照度は「直近N分/N時間のsensor_logsを都度集計」すれば継続的な状態を保持する必要はない(ステートレスに計算可能)。
一方、温度・土壌水分の「基準外が続いている開始時刻」は都度ログを遡って計算するより、状態が変わった瞬間に記録しておく方が軽量:

```
plants テーブルに追加
- temp_out_of_range_since (NULLABLE)
- soil_out_of_range_since (NULLABLE)
```

- センサー受信時(`POST /sensor`)に基準外かどうかを判定し、基準外に入った瞬間だけこのカラムに現在時刻をセットする。基準内に戻ったらNULLに戻す。
- 継続時間 = 現在時刻 − `*_out_of_range_since`

### 4-4. 日次レポート(湿度・照度)の結果保持

湿度・照度は評価結果を次の評価(翌日15:00)まで保持し続け、ホーム画面のバッジ表示(3-6章)にも使うため、`plants`テーブルに以下を追加する。

```
plants テーブルに追加
- humidity_daily_status (healthy / caution / needs_care)
- humidity_daily_avg (直近評価時の24時間平均値)
- humidity_evaluated_at (直近評価を実施した日時)
- illuminance_daily_status
- illuminance_daily_avg (直近評価時の昼間平均値)
- illuminance_evaluated_at
```

v1は1植物のみのためこの形で問題ないが、複数植物対応時は植物ごとに持たせる前提で設計してある。

## 5. 判定処理をどこで行うか

`POST /sensor`受信時(既存の`sensorController.js`)に以下を追加する形が自然。温度・土壌水分(リアルタイム系)と湿度・照度(日次レポート系)で処理タイミングが異なる点に注意。

**リアルタイム系(温度・土壌水分、受信のたびに評価)**

1. 受信したセンサー値を`sensor_logs`に保存(既存処理)
2. `plants`の`*_out_of_range_since`を更新し、継続時間を計算
3. レベルを算出し、悪化方向への遷移であれば6章の通知ロジックを呼び出す

**日次レポート系(湿度・照度、15:00をまたいだ最初の受信でのみ評価)**

1. 受信時、`humidity_evaluated_at` / `illuminance_evaluated_at`が「今日の15:00より前」であれば、直近24時間分の`sensor_logs`を集計して評価を実施する(6-5章参照)。
2. 評価結果を`humidity_daily_status`等に保存し、`*_evaluated_at`を現在時刻に更新する。
3. 要ケアであれば通知を生成する。
4. 同日15:00以降にさらにセンサーを受信しても、`*_evaluated_at`が既に本日分に更新済みのため再評価は行わない(1日1回に保つ)。

**共通**

- 4項目のレベルが揃った時点で、worst-ofで`plants.status`を更新する(表示用。3-5章参照)。

データ量が少ない(v1は1植物のみ)ため、都度集計で十分な性能が出るはず。将来的にデータ量が増えたら、定期バッチでの事前計算に移行を検討する。

## 6. 通知設計

以下6-1〜6-4は**リアルタイム系(温度・土壌水分)**の通知ルール。湿度・照度の通知ルールは6-5章を参照。

### 6-1. 通知を出すタイミング

- **状態が悪化方向に遷移した瞬間のみ**通知を生成する(例:適正→注意、注意→要ケア、適正→要ケア)。
- 同じレベルに留まっている間は再通知しない(「毎日開かなくてもいい」というコンセプトに合致)。
- 回復方向(注意→適正 など)は通知を出さず、ホーム画面の表示更新のみで十分。

### 6-2. 長期化した場合のリマインド

- 「要ケア」が**6時間以上**解消されない場合、リマインド通知を1回追加する(その後さらに継続しても再リマインドはしない。放置による通知疲れを避けるため)。
- 「注意」の長期放置については、現時点ではリマインドなし(要ケアに格上げされた時点で通知される設計のため)。

### 6-3. 通知メッセージの優先順位

複数項目が同時に悪化した場合、通知メッセージは最も深刻な項目を優先して1件生成する(項目ごとに個別通知を乱発しない)。

### 6-4. 夜間の通知抑制(サイレントタイム)

深夜の通知を避けるため、指定した時間帯は通知の生成を保留する。

- 対象時間帯は**固定値でハードコードせず**、既存の`NOTIFICATION_SETTINGS`テーブル(`system-design.md 6章`のER図に既にある`start_time`/`end_time`)を使う。デフォルト値は`start_time = 20:00` / `end_time = 06:00`とし、F-09(通知設定画面)から将来変更できるようにする。
- **保留の仕組み**:サイレントタイム中に状態が悪化(遷移)しても、その場では通知を生成しない。`plants`に`pending_notification`(悪化を検知した、まだ未通知というフラグ)を立てておくだけにする。
  - 続けてさらに悪化しても、フラグを立て直すだけ(通知は積み上げない)。
  - サイレントタイム中に状態が回復した場合は、`pending_notification`をクリアする(治ったことを検知していない古い警告を朝に届けない)。
- **解禁時の挙動**:サイレントタイムが終わった後、最初に`POST /sensor`を受信したタイミングで`pending_notification`が立っていれば、**そのときの最新の状態**を元に通知を1件だけ生成し、フラグをクリアする。夜間に何度状態が動いても、朝に届く通知は最大1件。
- **サイレントタイム中でも要ケアの記録自体は残す**:通知(プッシュ・アラート一覧への表示)は保留するが、`plants.status`自体はセンサー受信のたびに正しく更新しておく。ユーザーが夜中にアプリを開けば最新状態は見える(通知だけを止める設計であり、状態把握自体は止めない)。
- サイレントタイムをまたいだ「継続時間」判定(3章の要ケア継続6時間など)は、時計上の経過時間としてそのまま計算してよい(夜間だからといって継続時間のカウントを止める必要はない)。
- **解禁時刻ちょうどに通知を出す仕組みは持たない(方針確定)**。「解禁後、最初にセンサーを受信したタイミングで判定・通知する」で十分とする(A案)。ESP32の送信タイマーは`millis()`基準で壁時計と同期していないため、「厳密にend_timeちょうどに測定させる」ことはそもそも不可能であり、サーバー側で別途定期チェック(スケジューラ)を持たせる案(B案)は見送る。本番の送信間隔(8章参照)を10分にした場合、通知は最大でend_timeから送信間隔分(最大10分程度)遅れる可能性があるが、「そっと知らせる」というコンセプト上許容範囲とする。

### 6-5. 日次レポート系(湿度・照度)の通知

- 通知は**1日1回、15:00をまたいだ最初のセンサー受信タイミングで判定**する(5章参照。サイレントタイムと同じ「スケジューラを持たずセンサー受信をトリガーにする」設計パターンを踏襲している)。
- 評価結果が**要ケアの場合のみ**通知を生成する(適正・注意では通知しない。これは温度・土壌水分の「悪化した瞬間に通知」とは異なるルール)。
- 湿度・照度が両方とも要ケアだった場合も、6-3章と同様に1件にまとめる。
- リアルタイム系(温度・土壌水分)の通知と湿度・照度の日次通知が同じタイミングで重なった場合も、6-3章のルールに従い最も深刻な項目を優先して1件にまとめる。
- 15:00の評価タイミングがサイレントタイム(6-4章、デフォルト20:00〜06:00)と重なることは通常ないが、将来ユーザーが`start_time`/`end_time`を変更して重なるケースに備え、日次レポートの通知も6-4章の保留ロジックの対象に含める。

## 7. 実装の優先順位(参考)

今回の簡略化(湿度・照度の日次レポート化)により、実装コストの見通しが立てやすくなった。優先順位の目安:

1. リアルタイム系(温度・土壌水分)の継続時間判定・通知(6-1〜6-3)
2. サイレントタイム(6-4)
3. 湿度・照度の日次レポート評価・通知(3-2, 3-4, 6-5)
4. ホーム画面のバッジ表示切り替え(3-6)
5. 水やり記録機能(4-2)・季節別土壌水分閾値(3-3)

## 8. センサー送信間隔について(方針決定・実装は保留)

- 現状の`SEND_INTERVAL`(ESP32側)は開発・検証用に30秒としているが、本番運用では**10分間隔に変更する方針を確定**する。
  - 理由:温度・湿度・照度の変化速度に対して30秒は過剰であり、履歴データ量・サーバー負荷の観点でも10分で十分。湿度・照度が日次レポート化されたことで、送信間隔とリアルタイム移動平均の整合性を気にする必要もなくなった(温度・土壌水分は瞬間値、湿度・照度は24時間集計のため、10分間隔でもサンプル数は十分)。
- **実装は後回しとする**。設定周りの動作確認が完了するまでは30秒のまま検証を継続し、確認が終わり次第`plant_sensor_integrated.ino`の`SEND_INTERVAL`を書き換える。
- 送信間隔を延ばすだけではバッテリー消費はあまり改善しない点に注意(Wi-Fi接続を張りっぱなしにしているため)。本格的な省電力化(deep sleepの導入)は本件とは別タスクとして扱う。
